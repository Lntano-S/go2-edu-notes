# 提交

## 它是什么

一次提交（commit）= 一份快照 + 一句说明。快照说"这一刻这些文件长这样"，说明说"我为什么这么改"。历史，就是这些提交一节一节串起来的链条。

提交信息不是写给别人看的。半年后回来翻，能不能读懂当初为什么动这一行，全看它。

## 一句话讲清一次改动

格式：

```text
<类型>(<范围>): <做了什么>
```

| 类型 | 什么时候用 |
|---|---|
| `feat` | 新增板块、页面、功能 |
| `docs` | 纯内容、文档措辞 |
| `fix` | 修错字、坏链、逻辑错 |
| `style` | 只动样式排版 |
| `refactor` | 结构重排，行为不变 |
| `chore` | 依赖、配置、构建、杂活 |
| `ci` | 改 CI / 部署配置 |

范围可选，写板块名：`linux` / `guide` / `theme` / `ci` / `repo`。

三条写作规则：**动词开头**（补、加、修、换、拆），**一句话不加句号**，**一次只说一件事**。

本站真实的历史长这样：

```text
feat(linux): 新增 Linux 基础板块；首页卡片改为学习路径
docs: 补 404 页面、更新 README、去掉重复的空模板
chore: Node 版本对齐到 24（KaTeX 插件要求 >=22）
```

## 原子提交

一次提交只装一件事。加了新页面就提交新页面，改了样式就单独提交样式，别攒到最后来一句"更新一堆东西"。

好处有三个：翻历史时每条都读得懂；出问题时能精准回滚到某一处；将来要给别人看改动，一条提交就是一个完整的意思，不用替他拆。

本站在这条上走得比较狠：**一个页面一个 commit**。代价是提交条数多，换来的是每条都能独立读懂。

## 常用命令

```bash
git status          # 现在有哪些改动
git diff            # 具体改了什么，提交前一定看一眼
git add <文件>       # 把某个文件放进暂存区
git commit -m "…"   # 把暂存区记成一次提交
git log --oneline   # 一行一条地看历史
```

## 常见坑

- **`git add .` 一把梭**。会把不想提交的东西也塞进去（编辑器配置、临时文件）。`.gitignore` 就是干这个的：先把该忽略的写进去。
- **message 写成"更新"**。等于没写。说清改了什么、为什么改。
- **提交前不看 `status` 和 `diff`**。最常见的翻车方式：把两个不相干的改动混进同一条提交。
- **一次提交塞太多**。五件事挤在一起，回滚任何一件都得连坐。
